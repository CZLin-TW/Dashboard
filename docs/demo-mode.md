# Dashboard 獨立測試模式

v1.42.0：空調控制區可展開「溫度回饋補償」，測試啟用、同房間感測器與五個進階參數的保存／重讀。正常資料示範舒適目標 26°C、IR 下發 25°C；保存或停用不操作模擬設備，手動送出空調設定才更新 IR 值。此模式不模擬房間熱力學或定時補償，不能用來判斷實際冷氣多久能達標。

使用現有首頁、設備、照明、待辦、庫存頁面和元件，搭配固定的「測試成員」模擬身分。
不需要 LINE 配對、不簽發正式 session，也不用建立 Google Sheets 家庭成員。

## 新 Session 接手

測試模式已納入版本庫，取得包含此功能的最新程式碼即可使用，無須依賴先前的聊天紀錄。

1. 在 Dashboard 專案目錄工作，確認有 `npm run demo` 指令與本文件。

3. 開啟頁面並確認黃色測試模式列；需要一致的測試起點時按「重設資料」。
4. 測試報告分清楚模擬操作、真實後端整合及實機瀏覽器驗證。

## 本機啟動

```sh
npm ci
npm run demo
```

開啟 http://127.0.0.1:3001 。請使用獨立工作目錄，不放正式 `.env.local`。
模式由伺服器變數 `DASHBOARD_DEMO_MODE=1` 啟用；預設關閉，網址參數與 cookie 無法啟用。

頂部黃色列會一直顯示「測試模式 · 模擬家庭」。可選正常資料、空資料、設備離線、API 失敗。
切換情境會重設模擬資料；「重設資料」可重跑目前情境。

每個瀏覽器分頁使用自己的 sessionStorage；重新整理保留操作，關閉分頁即結束。
可持久化的查詢快取與釘選在測試模式改存 sessionStorage；私人查詢快取維持只存記憶體。模擬資料本身存在該分頁的 sessionStorage。身分切換／登出的共用清理仍可能移除舊的 `cache:` 項目，建議使用獨立來源與瀏覽器測試環境。
瀏覽器「複製分頁」可能複製初始資料，此後兩邊獨立。資料只存瀏覽器，不含真實家庭紀錄。

## 能測試什麼

- 桌機、手機的真實版面、卡片展開、釘選、圖表和載入流程。
- 冷氣設定與送出後狀態輪詢；手動除濕、啟停自動模式的控制鎖。
- 模擬照明開關、亮度、場景、效果、通知，以及夜燈規則表單儲存。
- 待辦與食品新增、修改、刪除／完成，唯讀待辦限制和私人項目的前端過濾。
- 排程新增、編輯、刪除；週期模板新增與停止；劇院功能開關。
- API 失敗與設備離線時既有 UI 的錯誤處理，方便發現沒有顯示錯誤或錯誤樂觀回饋的地方。

這是 **UI 功能沙盒，不是後端整合測試**：不驗證 LINE／JWT 登入、真實權限、Google Sheets、
家電收訊、感測器、推播或背景排程。歷史圖表為每次讀取生成的模擬曲線。
除濕規則只模擬表單設定、啟用時的即時判斷及控制鎖，不模擬完整狀態機或分時運轉；
夜燈和排程不背景執行，週期模板不自動生成下一筆待辦。未實作的 API／方法回 501，絕不假裝成功。

## 隔離措施

1. 只有獨立 local／Vercel Preview 環境可啟用；`VERCEL_ENV=production` 與 demo 同時設定會拋錯。
2. demo 環境若含 `HOME_BUTLER_API_KEY`、`SESSION_JWT_SECRET` 或 `LINE_LOGIN_CHANNEL_SECRET`，直接拒絕執行。
3. 瀏覽器先安裝模擬請求處理器，才掛載原有 UI；API 不會退回真實 fetch，外部 fetch 也拒絕。
4. 伺服器 proxy 在公開路由白名單之前攔截所有 `/api/*`，包含登入和未來新增的 API，統一回 503。
5. 即使繞過 proxy 執行 route，`butler.ts` 也會阻擋所有後端呼叫。
6. 正式模式仍然使用原本 LINE 配對、JWT 與角色限制，沒有通用測試密碼。

需要分享網址時，另建 Vercel Preview，僅設定 `DASHBOARD_DEMO_MODE=1`，不要複製正式 secrets。
一般自架 `NODE_ENV=production` 的建置／啟動也可在獨立測試主機使用，必須自己維持獨立網址與環境。
將程式碼推送到正式分支不會自動啟用 demo；一般正式網站仍走原本登入流程。

## 維護入口

| 檔案 | 用途 |
| --- | --- |
| `scripts/demo.mjs` | 本機啟動指令、位址與連接埠 |
| `src/lib/demo/config.ts` | 伺服器端啟用條件、憑證與環境限制、測試身分 |
| `src/lib/demo/fixtures.ts` | 虛構資料與測試情境 |
| `src/lib/demo/simulator.ts` | 模擬 API、資料寫入與請求隔離 |
| `src/components/demo/provider.tsx` | 安裝模擬請求處理器、分頁儲存、情境列 |
| `src/proxy.ts`、`src/lib/butler.ts` | 伺服器 API 與後端轉送隔離 |
| `tests/demo.test.ts` | 資料契約、互動與隔離測試 |

新增頁面或 API 時同步維護模擬資料與測試；瀏覽器出現 501 通常表示該模擬端點尚未實作。

首頁採按需載入：初始不讀圖表歷史與排程；點「查看環境趨勢」、設備控制面板、除濕機「濕度趨勢」分別觸發對應資料。檢查載入／失敗／空資料提示，以及收合後定期更新停止。模擬器支援 `include_weather=false`、`include_history=false` 與感測器 `name` 篩選；摘要仍需保留 CO₂ 與目前濕度。這些新舊資料契約都有 `test:demo` 檢查。
不要用連接真實後端的 fallback 掩蓋缺少的模擬端點。

## 驗證

```sh
npm run test:demo
npm run lint
npm run build
```

測試涵蓋各頁資料契約、CRUD、狀態輪詢、重新載入／分頁隔離、錯誤情境、未知 API 拒絕、
正式登入維持 401，以及伺服器後端呼叫次數為零。新增頁面／API 時需補 simulator 與契約測試。

## 排程結果（v1.36.0）

正常情境含客廳冷氣「執行失敗」與循環扇「待確認」範例。開啟設備控制面板，檢查原因、狀態標記與移除紀錄；這兩類不提供編輯或自動重送，確認設備後可另建排程。移除只刪指定執行識別碼的紀錄，不撤回已送出的指令。一般待執行排程仍可編輯、刪除。

Dashboard 讀取 `/api/schedules?include_attention=true`；後端預設仍僅回待執行，部署時先更新 home-butler 再更新 Dashboard。新欄位為 `執行識別碼`、`執行結果`，刪除注意紀錄需附 `execution_id`。真實執行與跨重啟保護由後端離線測試驗證，demo 不執行計時器或真實指令。

## 待辦與快取驗證（v1.37.0）

模擬資料 schema 為 2，舊 session 資料自動重設。API 回應只含測試成員的私人待辦與公開項目；隱藏的其他成員事項仍存在 fixture，可由離線測試驗證無法透過 ID 操作。待辦改名後再完成，應仍操作同一待辦ID；Notion 完成留記號。

正常畫面應無讀取錯誤提示；切換「API 失敗」應顯示讀取失敗與重試。回復正常後提示應消失。快取併發、保留成功資料、舊回應覆蓋與登出隔離使用 `tests/query-store.test.ts` 驗證；模擬模式不替代實際登入權限測試。

## 劇院模擬與驗證界線

劇院區塊包含三個開關與可選健康欄位；儲存時三個開關均暫停操作，完成後回讀。fixtures／simulator 提供模擬回應，沒有連接 KEF 事件通道或真正重啟 agent。
